## 一、已取得成果

### 1.1 开源代码

项目代码已在 GitHub 开源（`https://github.com/1hzl/low-precision-fft`），截止中期检查共包含 57 个文件、约 13,000 行代码。代码覆盖 GPU CUDA 内核开发、PyTorch C++ 扩展封装、Python 算法原型实现以及完整的自动化测试体系。项目采用 MIT 开源许可证，便于社区后续贡献和使用。

外部 API 设计简洁统一，仅需一行代码即可切换精度模式：

```python
import lowp_fft
X = lowp_fft.fft(x, precision="fp16")   # cuFFT FP16 加速
X = lowp_fft.fft(x, precision="bf16")   # cuFFT BF16 加速
X = lowp_fft.fft(x, precision="fp8")    # 自研 BFP FP8
```

支持标准 PyTorch 参数（`n`、`dim`、`norm`），与 `torch.fft.fft` 接口高度兼容，可无缝替换现有代码中的 FFT 调用。自动微分（`torch.autograd`）完整支持，forward 和 backward 均通过 `gradcheck` 验证。不支持的精度-设备组合会自动 fallback 到 FP32 并发出警告，保证鲁棒性。

### 1.3 自研 BFP FP8 算法

当前主流低精度计算方案（FP16、BF16）虽广泛支持，但在内存带宽受限的边缘设备和超大规模模型推理中仍有压缩空间。FP8（8位浮点）能进一步将存储需求减半（每元素 2 bytes vs FP16 的 4 bytes），但直接逐算子使用 FP8 执行 FFT 会导致灾难性精度损失——累计量化误差使 SQNR 降至 ~0 dB，完全不可用。

为此我们设计并实现了块浮点（Block Floating-Point, BFP）FP8 FFT 算法。核心创新在于三点：

第一，**每阶段共享指数**。将 FFT 的每个蝶形计算阶段视为一个 Block，块内所有元素共享一个指数因子。这样做的好处是：蝶形计算内部使用 float32 全精度，仅在阶段输入/输出边界进行一次量化/反量化，从而将量化次数从每次乘加降低到每个阶段一次，大幅压缩误差累积。

第二，**蝶形 float32 全精度计算**。BFP 仅在存储格式上使用 FP8（E4M3），但实际 FFT 蝶形运算完全在 float32 精度下执行。这确保了 FFT 核心计算的数值质量不受低精度存储的影响。

第三，**bit-reverse 与 per-stage DIT 流程**。CUDA kernel（846 行）从全局内存读取 FP8 数据，先反量化到 float32 再做时域抽取（DIT）蝶形运算，每阶段完成后重新量化回 FP8 写入全局内存，供下一阶段使用。

实验结果表明：相比 naive FP8 逐算子量化方案（SQNR 约 0 dB，完全不可用），BFP 方案达到约 21 dB 的 SQNR，提升幅度超过 20 dB。这一精度水平在实际应用中已具备工程实用价值。算法同时提供 Python 原型（用于快速迭代和验证）和 CUDA kernel（用于实际部署），两者数值结果完全一致。

### 2.2 已完成工作详述

**Phase 1（6月2日）— CUDA 环境验证与 Hello World**：在项目主力开发机（RTX 5070 Ti Laptop, CUDA 13.3, PyTorch 2.11）上完成 CUDA Toolkit 安装配置，编写并运行 cuFFT FP16 最小可工作示例。验证了 `cufftXtExec` API 的 FP16 数据路径可达、CUDA 与 PyTorch 的 tensor 互操作正常，确认完整开发环境可用。同步建立了 Git 仓库、CI 流水线（pytest + pytest-cov）和项目文件结构。

**Phase 2（6月3日）— FP16/BF16 cuFFT 集成 PyTorch**：这是项目工作量最大的阶段。核心工作是编写 PyTorch C++ 扩展（`lowp_fft_cufft.cpp`），将 NVIDIA cuFFT Xt API 封装为 PyTorch 可调用的算子。具体包括：

- 实现 `torch.autograd.Function` 子类，forward 调用 cuFFT，backward 使用共轭对称性复用 forward 的 FFT Plan（避免重复创建），大幅降低显存和延迟开销。
- 实现 PlanCache 机制：使用 double-checked locking 模式保证线程安全，缓存最近 64 个 Plan，Plan 命中时直接复用，避免每次调用重新创建 cuFFT Plan。
- 支持 `n`（FFT 点数）、`dim`（变换维度）、`norm`（归一化方式）参数，与 `torch.fft.fft` 接口兼容。
- 实现全自动 fallback：当指定精度在当前设备上不支持时（如 CPU 请求 FP16、Volta GPU 请求 BF16），自动降级到可用精度并发出警告。

该阶段产出的 C++ 扩展约 800 行，Python 封装约 600 行，通过 gradcheck（自动微分正确性验证）和 31 项基础测试。

**Phase 3（6月4日）— FP8 BFP 全链路**：从零开始研发块浮点 FP8 FFT。完整链路包括：

## 四、项目存在问题及解决方案

### 4.1 主要问题

**问题一（🔴 高优先级）— CPU SIMD 多架构适配完全空白**

任务书中明确要求"CPU 端 SIMD 多架构适配"，覆盖 x86 AVX2/AVX-512、ARM NEON/SVE、以及可选的 RISC-V RVV。截止中期检查，这一模块的代码行数为零。GPU 端的成功经验（cuFFT 封装 + 自研 BFP kernel）不能直接迁移到 CPU，因为 CPU 端没有 cuFFT 这样的成熟库可用，所有 FFT 蝶形计算需要从零开始使用 SIMD intrinsic 实现。这是下半年最高优先级的任务，也是决定项目最终完成度的关键。

**问题二（🟡 中优先级）— LLM 微调场景验证未开展**

任务书的应用场景定为"LLM 微调中的 FFT 加速"。虽然我们已经建立了 GPU 端的精度和性能基准数据，但尚未在真实的 LLM 微调工作流中端到端验证低精度 FFT 的效果。关键问题是：低精度 FFT 引入的 ~21 dB SQNR 噪声，是否会导致 LLM 微调过程中的梯度发散或收敛速度显著下降？这直接决定了项目的应用价值能否成立。没有这个验证，结题答辩和论文投稿都会受到质疑。

**问题三（🟡 中优先级）— BFP FP8 CUDA kernel 性能不理想**

当前 BFP FP8 CUDA kernel 的实测性能仅为 FP16 cuFFT 的约 0.01 倍，远未达到实用水平。主要瓶颈在于：每次 Python 调用 CUDA kernel 前需要额外的反量化 kernel（FP8→float32），调用后又需要再量化 kernel（float32→FP8），导致多次 Python↔CUDA 边界跨越和中间结果的显存读写。理想方案是将量化-蝶形-再量化融合为单个 CUDA kernel，消除中间步骤的开销。

**问题四（🟡 中优先级）— 多架构 CPU 测试环境未就绪**

ARM 云实例和 RISC-V 开发板目前均未采购。ARM 交叉编译无法在本地 x86 机器上完成端到端验证（qemu-user 可以运行但无法测试 SIMD 性能），RISC-V 更是完全没有接触过。测试环境的缺位直接阻塞了问题一的解决。好消息是经费已预留，采购流程没有技术障碍。

**问题五（🟢 低优先级）— PyTorch 社区贡献流程未研究**

将项目代码贡献至 PyTorch 官方是任务书的终极目标。但目前我们对 PyTorch 的 Contribution Guide、CI/CD 流程、代码风格规范、PR review 机制等一无所知。不过这个问题在逻辑上排在 LLM 验证和 CPU 适配之后，优先级较低，计划在 Phase 7 启动。

### 4.2 解决方案

**问题一（CPU SIMD 多架构适配）**

Phase 5 启动，采用分架构逐步推进的策略。第一步实现 x86 AVX2（利用现有开发环境，Intel Intrinsics Guide 参考），这是开发成本最低、可以立刻动手的部分。第二步实现 ARM NEON（需要租赁 ARM 云实例后开始，参考 ARM ACLE 规范），NEON intrinsic 的编程模型与 x86 SSE/AVX 相似，经验可部分迁移。第三步探索 RISC-V RVV（采购开发板后启动），RVV 采用向量长度不可知（VLA）的编程模型，与传统的固定宽度 SIMD 有本质差异，需要额外学习成本，但其灵活性为学术创新提供了空间。三层之间通过编译时宏定义实现指令集自动检测与适配，共享统一的 C++ 接口（`cpu_fft_fp16` 等），上层 Python 封装不感知底层指令集差异。

**问题二（LLM 微调场景验证）**

Phase 6 启动。参考 BCA 论文（arXiv 2505.00582）中 FFT 在 LLM 微调中的具体使用路径（如 FFT-based attention approximation 或 Fourier domain parameter-efficient fine-tuning），构建覆盖典型 LLM 序列长度（512/1024/2048/4096）和 batch 规模（1/4/8）的测试集。对比低精度 FFT 与原生 FP32 FFT 在以下维度的差异：训练 loss 曲线（梯度收敛速度和最终 loss 值）、下游任务指标（如 perplexity 或 accuracy）、显存占用和吞吐量。如果低精度 FFT 导致的 loss 偏差在可接受范围内、同时带来可观的显存节省或加速，则可确认为应用价值成立。

**问题三（BFP FP8 CUDA kernel 性能优化）**

核心策略是融合。将当前分离的三个步骤（反量化 → 蝶形 FFT → 量化）合并到一个 CUDA kernel 中执行。具体做法是：在共享内存中维护 float32 中间结果，整个阶段的蝶形计算在 float32 精度下完成，完成后直接在 kernel 内进行 FP8 量化并写回全局内存。这样消除了两次 GPU kernel launch 的延迟开销，以及两次全局内存往返的数据搬运。预期优化后性能可提升到 FP16 的 0.3–0.5 倍，达到实用水平。

**问题四（多架构 CPU 测试环境）**

结合 3.2 节的经费安排，两条线并行推进。ARM 线：申请 ARM 云实例（预算 ¥1,000），优先选择提供 ARM NEON 和 SVE 的开发实例。开发前先用 QEMU 用户态模式在本地 x86 机器上完成 ARM 二进制的基础编译和逻辑测试（不涉及 SIMD 性能），减少云实例的计费时长，仅将最终 SIMD 验证和调优放在云实例上进行。RISC-V 线：采购开发板（预算 ¥1,500），本地 USB/TTL 连接，在板上直接编译和运行测试。

**问题五（PyTorch 社区贡献流程）**

Phase 7 启动。首要任务是完整研读 PyTorch Contribution Guide（GitHub 上的 CONTRIBUTING.md 和相关 Wiki 页面），了解从 Issue → RFC → PR → Review → Merge 的完整流程。同时调研社区中已合并的低精度相关算子 PR 作为参考案例（如 FP8 相关的 `torch._scaled_mm` 等），分析它们的 PR 描述格式、测试要求、性能基准呈现方式，制定提交策略。

### 4.3 下一步计划

**Phase 5（2026年6–7月，🔴 最高优先级）**：CPU SIMD 多架构适配。按照 x86 AVX2 → ARM NEON → RISC-V RVV 的顺序逐步推进。x86 AVX2 在本地开发环境即可进行，ARM NEON 需要完成云实例租赁，RISC-V RVV 需要完成开发板采购。产出包括 C 扩展（SIMD intrinsic 实现）、`lowp_fft.fft(x.cpu(), precision="fp16")` 可用接口、x86+ARM 双架构编译通过、精度与 GPU 版本一致性验证报告。

**Phase 6（2026年7–8月，🟡 高优先级）**：LLM 微调场景验证与 BFP CUDA kernel 性能优化。LLM 验证方面，构建基于 BCA 论文的测试工作流，重点回答"低精度 FFT 是否影响模型训练质量"这一核心问题。BFP 性能优化方面，完成量化-蝶形-重量化 kernel 融合，目标性能达到 FP16 的 0.3 倍以上。此外，使用经费租赁 H100/A100 实例，评估原生 FP8 FFT 路径，作为 BFP 方案的对比基线。

**Phase 7（2026年8–9月，🟢 中等优先级）**：PyTorch 社区规范研究与 Initial PR 准备。系统学习 PyTorch 贡献流程，整理代码使其符合社区风格规范，撰写 RFC（Request for Comments）描述项目动机和技术方案，准备包含核心功能的首次 PR。

**Phase 8（2026年11–12月，🟢 常规优先级）**：社区反馈迭代与项目收尾。根据 PyTorch reviewer 的反馈修改代码和文档，可能涉及多轮 PR 迭代。同步完成结题答辩准备和结题报告撰写，整理全部技术文档和实验数据归档。
